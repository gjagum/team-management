One app for people,
time off, and hours logged.

A React single-page app talking to a Hono API on Bun, backed by PostgreSQL through Prisma. Employees request leave and overtime; managers and team leaders approve them; admins own the permission matrix. Everything else — teams, schedules, timesheets, documents, onboarding — hangs off the same employee record.

03 — The data model

User is the account. Employee is the person.

They are deliberately split: a freshly created user has a role and a login but no employee profile until an admin “activates” one. Every domain table below hangs off Employee, not User.

👤 People

  • User — email, bcrypt hash, role, isActive
  • Employee — code, dept, position, hire date, salary, teamId, slackId
  • Team — leaderId + alternateApproverId (both unique)
  • Session — token row, expiresAt

🌴 Leave & overtime

  • LeaveRequest — days, paid/unpaid split, status, reviewer
  • LeaveBalance — per employee per year: total vs used
  • OvertimeRecord — date, start/end, hours, status

⏱ Time

  • Schedule — one row per employee+date, shift type
  • DefaultSchedule — per employee+dayOfWeek, has isOff
  • TimeLog — one row per employee+date, clockIn/Out, source

📄 Paperwork

  • EmployeeDocument — type, size, mime, expiry, status
  • OnboardingTask — required flag, category, sortOrder, completedBy

⚙️ System

  • Permission — resource + action + name
  • RolePermission — role ↔ permission grant
  • AppSettings — typed key/value, grouped by category
  • AuditLog — action, entity, oldValues, newValues

🔗 The spine

  • User 1 ── 0..1 Employee
  • Employee * ── 1 Team
  • Employee 1 ── * everything else
  • Approvals point back at an Employee, not a User — so "who approved" is always a person on staff.
04 — Who can do what

Four roles, one editable matrix

Capabilities are rows in role_permissions, not code. An admin can hand a permission to a role at runtime and the next request honours it. Role checks still exist alongside for hard boundaries — like team scoping.

AdminADMIN

Can

  • Everything: users, employees, teams, schedules, documents, onboarding
  • Edit the permission matrix at /rbac
  • Change global settings (company name, currency, overtime multiplier)
  • Approve anything — no team scoping applies

Still can't

  • Bypass the session table — logging out invalidates the token for real
  • Skip the audit log on a mutation
ManagerMANAGER

Can

  • See all leave and overtime requests, not just their own
  • Approve / reject with review notes
  • View reports and generate timesheet PDFs

Can't

  • Manage users or the permission matrix
  • Edit settings
  • Change team composition
Team LeaderTEAM_LEADER

Can

  • Approve leave/overtime only for members of a team they lead
  • Manage schedules for that team
  • Acts as alternate approver when assigned on the team

Can't

  • Approve across teams — handler returns 403
  • Reach admin surfaces, even with a stray permission
EmployeeEMPLOYEE

Can

  • Create own leave and overtime requests
  • See own balance, own requests, own schedule
  • Cancel a still-pending request
  • Clock in/out by messaging the Slack bot

Can't

  • See anyone else's requests — list is filtered by employeeId
  • Approve anything

05 — Three flows worth knowing

Leave, overtime, and the Slack clock

🌴 Requesting leave accrual

Balance is earned, not granted

computeAccruedLeaves() prorates leave.annual_allowance (default 15) by days worked this year, from hire date.

Paid / unpaid is split at creation

Paid days = min(requested, remaining balance). The rest lands in unpaidDays.

Overlap is rejected

Any PENDING or APPROVED request touching those dates returns 400 before insert.

Approval only moves paid days

On approve, usedLeaves increments by paidDays via upsert.

Delete means cancel while pending

Only a PENDING request flips to CANCELLED; otherwise the call is a no-op.

⏱ Logging overtime approval

Employee submits

Date, start, end, hours, description. Status starts PENDING. No balance maths — hours are recorded, not debited.

Team Leader or Manager reviews

Same team-membership guard as leave: a leader may only touch their own team's rows.

Timesheet consumes it

GET /timesheets/preview and POST /timesheets/generate turn approved hours, plus time logs, into a PDF with per-type multipliers.

💬 The Slack clock no auth

One public endpoint

POST /api/webhooks/slack — outside the auth middleware entirely.

Challenge, then events

Answers Slack's url_verification, then reads message events, ignoring bots.

Keyword mapping

"checkin" → clock in (only if unset). "checkout" → clock out (always latest).

Silent on unknown users

No matching slackId returns {ok:true} so Slack never retries or leaks membership.

🕐
Clock-in is first-wins and clock-out is last-wins for a given day, because time_logs has a unique (employeeId, date) pair.
06 — Sharp edges

Where the seams show

Found while reading the code — not fixed, just surfaced so they don't surprise you.

🐞
Wrong field name in the leave-creation fallback

leaves.ts reads employee.hiredDate, but Prisma exposes hireDate. That branch feeds undefined into the accrual maths, producing NaN totals.

🔀
Two different allowance defaults

/balance reads the leave.annual_allowance setting (default 15); the creation fallback hardcodes 20. A brand-new balance can start at either number.

📉
Accrual is frozen at first write

totalLeaves is set once when the balance row is created and never re-accrued, so the "earn as you work" figure drifts as the year advances.

🔓
Deactivation doesn't revoke access

Setting isActive = false is not checked by authMiddleware, so an existing session keeps working until it expires.

🧪
A little untyped hiding

appSettings is reached via (prisma as any) in the leaves route even though the model exists — a leftover from before it was generated.

📝
Docs say three roles, code has four

TEAM_LEADER exists in the schema, middleware and UI, but README and memory.md describe a three-role model.

07 — Running it

One command, three services

Docker (recommended)

  • docker-compose up -d
  • Frontend on :3000, API on :3001
  • Seed users are created on first boot
  • docker-compose down -v resets the database

Seeded accounts

  • admin@team.com / admin123
  • manager@team.com / manager123
  • employee@team.com / employee123
  • No Team Leader is seeded — promote an employee to test team approvals.
